## 1. 项目目标定义

**一句话定义**：一个开源、自托管的多 Agent 编排框架，让用户像经营真实公司一样经营一支 AI 员工团队：招聘（创建）→ 入职（人格/技能/模型配置）→ 派单（任务流转）→ 制度约束（评审/驳回/权限）→ 绩效考核（统计评估），组织随业务从"创业三元老"自动生长。

**北极星指标**：

| 指标 | 目标 |
|---|---|
| 真实任务完成率 | 预置 3 类任务在真实 LLM 下完成率 ≥ 2/3 |
| 安装到首个任务完成 | ≤ 5 分钟（演示模式） |
| 制度有效性 | 越权调用 100% 拦截；非法状态跳转 100% 拒绝 |

## 4. 系统架构

```
┌────────────────────────────────────────────────────────────┐
│ 界面层    Web 看板（单文件 HTML + REST）· CLI              │
├────────────────────────────────────────────────────────────┤
│ 编排层    Orchestrator：状态机引擎 · 派发器 · 调度器        │
│          （超时检测/升级提醒/驳回循环控制）                 │
├────────────────────────────────────────────────────────────┤
│ 组织层    Org：公司配置 · 部门树 · 岗位模板 · 权限矩阵      │
│          Employee：人事档案 · 生命周期 · 绩效账本           │
│          Identity：人机统一身份 · 支出授权审批               │
├────────────────────────────────────────────────────────────┤
│ 执行层    Runner：LLM 网关(多供应商) · 工具循环 · 审批闸门  │
│          Guard：合规双层（硬规则 + 检查单）                 │
│          Messenger：权限内点对点通信（强制入审计日志）       │
├────────────────────────────────────────────────────────────┤
│ 数据层    JSON 文件存储：任务/员工/消息/审批/审计/统计      │
└────────────────────────────────────────────────────────────┘
```

### 4.1 核心组件

| 组件 | 职责 | 关键接口 | 依赖 |
|---|---|---|---|
| StateMachine | 状态流转，合法转换白名单强校验 | `advance(task, action, actor)` | Store |
| Dispatcher | 按权限矩阵派发；失败重试 2 次 | `dispatch(task)` | PermissionMatrix, Runner |
| Runner | 员工干活引擎：prompt 组装 → LLM → 工具循环 → 产出 | `run(employee, task, context)` | LLMGateway, Tools, ApprovalQueue |
| LLMGateway | 统一 OpenAI 兼容协议；含 MockLLM（演示模式） | `chat(model, messages, tools)` | 配置 |
| ApprovalQueue | 高危/支出/编制审批：分级放行 + 容量/时间联合触发批量审批 + 优先级队列 | `request() → approve/reject` | Guard, Identity |
| Guard | 硬规则（黑名单/白名单）+ 检查单；判定操作风险等级 | `check(action)` / `review(plan)` | 规则配置 |
| Messenger | 员工间点对点消息，先过权限矩阵，全部落审计 | `send(from, to, task_id, text)` | PermissionMatrix, Store |
| Ledger | 绩效与成本：完成数/耗时/费用/驳回率；预算强制 | `record()` / `stats()` | Store |
| HumanInbox | 人类待办收件箱：认领、填结果、交还 | `list / complete` | StateMachine |
| Memory | 员工轻量记忆：经验条目、关键备注；验收评分回写 | `recall(emp_id)` / `record_experience(emp_id, entry)` | Store |

### 4.2 任务状态机

```
提交 → Pending → Triage(分拣) → Planning(规划) → Review(评审)
                       ↑              │驳回(≤3轮)
                       └──────────────┘
                                        │通过
        → Assigned(派发) → Doing(执行) ⇄ WaitingHuman(等待人类)
                                        │
        → Reporting(汇总) → Done ✅   （任意阶段可 Cancelled；失败即 Blocked + 原因）
```

- WaitingHuman：AI 发起人类子任务时进入，人类完成后自动恢复，超时提醒/升级；
- 支出授权不设独立状态，作为审批单挂起当前执行；
- 每次流转写 `flow_log`，进展写 `progress_log`（含 tokens/费用快照）。

### 4.3 关键数据流

提交 → 前台分拣 → PM 拆解（标注子任务执行者类型）→ 评审员双层检查（硬规则 + 检查单）→ 按权限矩阵派发 → 并行执行（高危操作走审批闸门；超能力转人类待办）→ 汇总 → 老板验收 → Done；全程成本入账。

### 4.4 技术决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 语言/依赖 | Python 3.10+，零第三方运行时依赖 | 安装体验是第一约束；edict-standalone 已验证该路线 |
| 存储 | JSON 文件（按组织目录隔离），临时文件+原子重命名 | 免数据库、可 git 化、审计可读；单机并发不构成瓶颈 |
| Web | 标准库 HTTP + 单文件 HTML（原生 JS） | 零构建 |
| CLI | argparse 子命令 | 零依赖 |
| 演示模式 | MockLLM 按角色脚本化应答，承诺永不抛错 | 保障 D1 路径稳定 |

### 5.1.1 Agent 工作环境（工位 / 记忆 / 成长）

借鉴同赛道产品（普渡机器人「Agent 员工管理平台」）的"环境 > 流程"思想，但**取其个体能力层、弃其去流程化主张**——我们同时保留 edict 的协作边界（状态机）+ 此处的个体能力（环境）：

| 环境要素 | laoban 轻量落地 | 说明 |
|---|---|---|
| **工位 Workspace** | 每员工独立工作目录 `workspaces/<id>/`，含任务队列、上下文快照、工作日志 | 补上"独立 Workspace"概念的数据落地 |
| **记忆 Memory** | 每员工一个 JSON 记忆文件，存 `experiences`（经验条目）+ `notes`（关键备注） | 结构化经验，非聊天记录；是"员工会成长"的地基 |
| **成长 Evolution** | 人类验收评分 → 结构化回写 `memory.experiences`（最简版经验回写） | 完整进化闭环（日/周/季度）推迟 v0.2 |

**数据主权与可解释性原则**（零成本，必须声明）：
- **数据主权归用户**：组织记忆、Agent 经验、任务数据全部落在用户本地数据目录，平台（框架）只是运行环境，不拥有数据；
- **可解释性**：每个关键决策（评审结论、驳回理由、审批、经验回写）必须能追溯到"谁、基于什么、为什么"——复用 flow_log / progress_log / 审计日志实现，不新增机制。

### 5.2 权限矩阵（三维度，岗位默认 + 个人覆盖）

| 维度 | 管什么 | 机制 |
|---|---|---|
| 协作权限 | 谁能跟谁点对点通信 | 岗位模板定义默认，个人覆盖；消息强制挂任务上下文并写审计 |
| 工具权限 | 谁能用什么工具 | `capabilities.tools` 白名单；高危工具叠加审批闸门 |
| 支出权限 | 谁能花多少钱 | 单任务限额 + 日预算；超限触发人类审批 |

以岗位角色为主、个人覆盖为辅，避免 N² 配置爆炸。

### 5.3 人机统一身份模型

```
公司（组织容器）
 ├── 人类账号
 │    ├── owner      老板：招聘/解雇、全量审批、验收、改一切配置（v0.1 唯一启用）
 │    ├── manager    部门主管：本部门支出审批/绩效查看（角色字段进 v0.1 数据模型，登录鉴权 v0.2）
 │    └── worker     人类员工：只处理派给自己的人类待办（同上）
 └── AI 员工（系统身份，不登录，以档案为凭据运行，行为全部入审计）
```

- 人 → AI：下达任务 / 审批 / 验收；AI → 人：派发人类待办（结构化：背景+目标+交付物格式+截止提醒）/ 请求授权 / 汇报；
- v0.1 已知妥协：本地运行、无登录鉴权、默认绑定 127.0.0.1 + README 醒目警告。

### 5.4 启动期「创业团队」模式（Phase 0）

```
1. 系统初始化 → 自动入职创业三元老：HR 专家 · 法务专家 · IT 专家
2. 老板输入业务构想
3. 三元老走标准流水线完成「组织设计」特殊任务：
   HR：梳理业务流 → 部门/岗位/职责拆解
   法务：业务合规审查（常识级红线提示，不构成法律意见）
   IT：各部门工具与权限建议
4. 产出《组织设计方案》→ 老板逐段审批（可驳回重拟）→ 批准
5. 方案落地：创建部门、生成岗位模板、设默认权限与预算
6. 老板任命部门负责人（AI 或人类占位）
```

### 5.5 双轨招聘（Phase 1）

```
轨道 A：老板直接招聘（应急保留）
轨道 B（主通道）：部门负责人提交编制申请（新增 AI / 复制 AI / 招聘人类）
   必含：理由 + 工作量依据 + 成本测算 → 老板审批 → HR 执行入职
```

复制员工继承档案，预算独立计算。

### 5.6 绩效面板

| 类型 | 指标 | 来源 |
|---|---|---|
| 客观统计 | 完成数、平均耗时、费用、驳回率、WaitingHuman 发起次数 | Ledger 自动采集 |
| 客观统计（核心新增） | **人类介入率** =（人类待办发起次数 + 审批次数 + 人工纠偏次数）÷ 总步骤数，衡量 AI 员工自主程度 | Ledger 自动采集 |
| 主观评价 | 成果质量、协作表现（1-5 星） | owner 验收时打分 |
| 自定义扩展槽 | 用户按任务上报业务指标（键值对），面板展示但不参与系统逻辑 | 任务上报 |

- 业务 KPI 不内置进框架（面向千行百业，内置具体业务指标属过度设计），由用户写入档案 `performance_goals.quality_bar` 并在验收时人工评价；
- 框架只负责"展示自定义指标"，不替用户定义业务含义。

### 5.7 默认模板（快捷方式）：软件开发公司（7 角色）

| 角色 | 岗位 | 权限特点 |
|---|---|---|

## 6. 错误处理、安全边界与测试

### 6.1 合规硬规则层（确定性执行，不依赖 LLM）

- 命令黑名单（默认 + 可扩展）：`rm -rf /`、`mkfs`、`dd`、`curl | bash`、强推生产分支等；
- 外部请求默认域名白名单制；携带上下文的数据外发强制审批（不可关闭）；
- 删除/覆盖工作区外文件强制审批（不可关闭）；
- 内容红线硬拦截 + 审计留痕。
- 架构级保证：ApprovalQueue 是高危工具调用的唯一通道，无绕过路径。

### 6.2 审批队列模型（统一三类审批 + 批处理）

**审批单结构**：
```
审批单 { id, 类型: 高危操作 | 支出超限 | 编制申请,
        发起人, 上下文摘要, 金额/影响, 优先级: normal | urgent,
        状态: pending → approved/rejected,
        审批人, 审批意见, 时间戳 }
```

**审批队列（ApprovalQueue）——容量/时间联合触发的异步批处理**（来源：外部研究报告机制思想，非其数据）：
- 审批单先进队列，不逐条弹窗打断老板；
- **容量触发**：同类待审批单攒满 N 条（默认 5）→ 打包成一批推送；
- **时间触发**：任一审批单等待超 T 秒（默认 120）→ 即使不满 N 条也强制推送，保证最低时效；
- **优先级通道**：`urgent` 审批单进独立队列，触发阈值更低（容量 1 / 时间 30 秒）；
- 队列长度、阈值均可配置；24h 未处理置顶提醒；任务挂起不算失败；全部留痕入审计。

**分级放行（Human-on-Exception）——autonomy_level 驱动**：
- `full`（全自主）+ 低风险操作 → 自动放行，不产生审批单；
- `semi`（半自主）→ 中风险才审批；
- `supervised`（受监管）→ 高风险/支出/编制一律审批；
- 风险等级由 Guard 硬规则 + 员工 autonomy_level 联合判定，高风险操作始终不可自动放行（底线不可关闭）。

### 6.3 错误处理分级 —— 核心原则：任务不允许静默死亡

| 故障 | 策略 |
|---|---|
| LLM 调用失败 | 指数退避重试 3 次 → `Blocked` + 原因上看板 |
| 员工停滞 | 180s 无进展标黄 → 10 分钟标红上报直属上级 |
| 驳回循环异常 | 第 3 轮仍驳回 → 强制中止，升级老板裁决 |
| 工具执行报错 | 错误回喂自修复 ≤2 轮 → 仍败 `Blocked` |
| 数据写入 | 临时文件 + 原子重命名，启动自检可回滚 |
| 演示模式 | MockLLM 永不抛错 |

### 6.4 测试金字塔

- 单元测试：状态机全路径 / 权限矩阵 / 预算计算 / Guard 规则 / 档案 schema 校验（状态机与权限模块 100% 路径覆盖）；
- 端到端（MockLLM）：正常路径 + 驳回循环 + WaitingHuman + 审批单；
- 冒烟测试：复刻干净环境安装链路（支撑 D1）；
- 人工验收：真实 LLM × 3 任务（D2，不可自动化）；
- CI：GitHub Actions，零依赖 `python -m unittest`。
